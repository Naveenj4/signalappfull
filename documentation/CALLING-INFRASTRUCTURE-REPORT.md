# PIT Messenger – Voice & Video Calling Infrastructure Report (Phase 1)

## 1. Executive Summary & Calling Engine
Voice and video calling in PIT Messenger are powered by Signal's native **RingRTC** library (an optimized WebRTC wrapper compiled with Rust and C++). 

Calling is **NOT** a frontend simulation or simple WebRTC demo:
- **Signaling**: WebRTC offer, answer, ICE candidates, and hangup signals are serialized into encrypted Signal messages (`SignalServiceCallMessage`) and transmitted via the server WebSocket connection.
- **Media Encryption**: Media streams (Opus audio, VP8/VP9/H.264 video) are encrypted end-to-end using SRTP / DTLS-SRTP.
- **Relay Traversal**: When devices cannot establish direct peer-to-peer (P2P) connections due to symmetric NAT or firewalls, traffic is relayed through a TURN server.

## 2. 1-to-1 Calling Signaling & Media Flow

```
Caller (Device 1)                       Signal Server                       Callee (Device 2)
       |                                      |                                     |
       | 1. GET /v2/calling/relays            |                                     |
       |------------------------------------->| 2. Returns Coturn STUN/TURN tokens  |
       | 3. Generates SDP Offer (Audio/Video) |                                     |
       | 4. Encrypts CallMessage via E2EE     |                                     |
       | 5. Sends Offer to Callee UUID        |                                     |
       |------------------------------------->| 6. Delivers Offer over WebSocket    |
       |                                      |------------------------------------>|
       |                                      |    [ Phone Rings with Incoming UI ] |
       |                                      | 7. User accepts call                |
       |                                      | 8. Generates SDP Answer             |
       |                                      | 9. Sends Answer over WebSocket      |
       |                                      |<------------------------------------|
       | 10. Delivers Answer                  |                                     |
       |<-------------------------------------|                                     |
       |                                                                            |
       | 11. ICE Candidate Exchange (via Server Signaling)                          |
       |<==========================================================================>|
       |                                                                            |
       | [ Direct P2P Media Stream (DTLS-SRTP Audio & Video) ]                     |
       |<-------------------------------------------------------------------------->|
       |                                                                            |
       | [ Fallback: Relayed Media via Coturn TURN Server if Symmetric NAT Blocks ] |
       |<----------------- Coturn Relay Server (Port 3478/5349) ------------------->|
```

## 3. Required External Infrastructure for Calling

### 3.1. Coturn STUN/TURN Server
- **Package**: `coturn` (Open-source RFC 5766/6156 TURN server).
- **Ports Required**:
  - `3478 UDP/TCP`: Standard STUN/TURN
  - `5349 TCP`: TLS-encrypted TURNS
  - `49152-65535 UDP`: Media relay range
- **Credential Generation**: Time-limited HMAC-SHA1 tokens generated by [`CallRoutingControllerV2.java`](file:///D:/signalappppp/signal-server/service/src/main/java/org/whispersystems/textsecuregcm/controllers/CallRoutingControllerV2.java).

### 3.2. Group Calling Infrastructure (SFU)
- While 1-to-1 calls are peer-to-peer, group calls (>2 participants) require a Selective Forwarding Unit (SFU) media server:
  - **Signal Calling Service / LiveKit / mediasoup**: Receives single upstream video/audio and forwards downstream streams to other participants.
  - **Status**: Group calling will be implemented in Phase 6 after 1-to-1 calling is verified.
